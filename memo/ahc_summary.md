# 第1章：開発・検証インフラ

この章では、ローカルでの検証手順と、実行結果の見方をまとめる。
まず `pahcer` で回し方を固定し、その後に JSON とサマリーを見て調整する。

## 1.1 ローカルテスタと実行環境（`pahcer` の利用）

手元の検証では、テストランナーである `pahcer` を使って実行と結果集計を行う。

### 実行方法

`rust` ディレクトリ内で次のコマンドを実行する。

```bash
pahcer run
```

### 実行の制御（`pahcer_config.toml`）

`pahcer_config.toml` を調整すると、テストケースの範囲や並列数を変更できる。

- **`start_seed` / `end_seed`**: 実行するテストケース（シード値）の範囲を指定する。
- **`threads`**: 同時実行数を指定する。
    - `1` に設定すると1件ずつ実行される。
    - `0` に設定すると複数件が同時に並列実行される。

### 実行結果の出力

実行が完了すると、`rust/pahcer/` ディレクトリ配下に結果が出力される。

- **`rust/pahcer/json/`**: 実行結果の詳細がJSON形式で出力されるディレクトリ。
- **`rust/pahcer/summary.md`**: 実行結果のサマリーが出力される。
- **`rust/pahcer/best_scores.json`**: ベストスコアの情報が保存される。

# 第2章：高速化・定数倍最適化（High-Speed Bit and Memory）

ヒューリスティックコンテストでは、同じ時間内により多くの状態遷移を評価できる実装が有利です。
ただし、最適化は「速そう」に見えるだけでは不十分で、問題構造に対して効果があるかを計測で確認する必要があります。
この章では、事実と意見、理論と実装を混ぜないように分けます。
読み方は単純で、2.1 は理論の事実、2.2 は実装の推奨、2.3 は計算量削減の定石、2.4 は応用例、2.5 は運用ルールです。

---

## 2.1 理論編：何を減らすと速くなるか

ここは事実ベースの説明であり、採用の是非ではなく「なぜ速くなるか」を扱う。

-   1. 再計算を減らす
       事実: 状態全体を毎回評価するより、変化した部分だけ更新した方が計算量は小さくなりやすい。
       局所変更で局所影響しか出ないなら、差分評価が成立する。

-   2. メモリアクセスを減らす
       事実: 計算よりもキャッシュミスや動的確保の方が遅いことが多い。
       連続メモリ化、再利用、局所性の改善でアクセスコストを下げられる。

-   3. 分岐を減らす
       事実: if の多いコードは分岐予測に失敗すると遅くなる。
       条件式の順序や branchless 化で、予測しやすい形に寄せられる。

-   4. 探索空間を減らす
       事実: 枝刈りや前処理で探索空間を減らせば、定数倍最適化より大きく効くことがある。
       計算量自体が下がれば、1回あたりの微調整より効果が大きい。

-   5. 事前計算に逃がす
       事実: 探索中に繰り返し出る値は、最初にまとめて計算しておくと、ループ内コストを削れる。
       テーブル参照に置き換わるだけでも効果がある。

-   6. 近似と厳密を分ける
       事実: 高コストな厳密評価を毎回やらず、まず粗い評価で候補を絞る二段階構成は有効である。
       最後だけ厳密に見る設計は、AHCでよく使われる。

## 2.2 実装編：定数倍を詰めるテクニック

ここは意見ベースの推奨であり、採用前提ではなく「使う価値がある候補」を並べる。

-   7. ゼロアロケーション（再利用）
    - 事実: 同じバッファを繰り返し使うなら、新規確保を減らすほどアロケータの負担は小さくなる。
    - 意見: 必要容量を先に確保し、配列は clear 相当で再利用するのがよい。
    - 適用条件: 同じバッファを繰り返し使う処理がある。
    - 期待効果: アロケータ呼び出し削減による安定高速化。
    - 注意点: クリア漏れによるゴミ参照に注意。

-   8. 多次元配列の1次元平坦化
    - 事実: 連続メモリの1次元配列は、Vec of Vec より局所性を確保しやすい。
    - 意見: 1次元化して、添字は y × W + x で計算するのが基本である。
    - 適用条件: グリッドやDP表を高頻度で走査する。
    - 期待効果: キャッシュヒット率改善。
    - 注意点: 添字計算ミスを防ぐため、変換関数を統一する。

-   9. AoSからSoAへの変換（Structure of Arrays）
    - 事実: 必要な属性だけを読むなら、属性を分けた方が無駄な読込を減らせる。
    - 意見: 特定属性だけを大量走査するなら、構造体配列より属性ごとの配列に分離するのが有効である。
    - 適用条件: 特定属性だけを大量走査する。
    - 期待効果: 不要データの読込削減。
    - 注意点: 可読性低下と更新漏れのリスクが上がる。

-   10. スタックメモリの積極利用
    - 事実: サイズが固定なら、ヒープ確保より固定長配列の方が軽いことが多い。
    - 意見: 小さく固定長の作業配列はヒープより固定長配列を優先した方がよい。
    - 適用条件: サイズ上限が小さく明確。
    - 期待効果: 確保コスト削減。
    - 注意点: 大きすぎる固定長配列はスタック圧迫を招く。

-   11. アリーナ方式の利用
    - 事実: 小さいオブジェクトを大量生成する処理では、個別確保・解放の回数がボトルネックになりやすい。
    - 意見: 巨大配列からインデックスで切り出す方式が有効である。
    - 適用条件: 生成順序が単調で個別解放が不要。
    - 期待効果: 確保と解放のオーバーヘッド削減。
    - 注意点: 世代管理や再利用設計が必要。

-   12. 差分評価（Delta Evaluation）
    - 事実: 局所変更で局所影響しか出ないなら、全再計算は無駄が大きい。
    - 意見: 遷移ごとに影響範囲の増減だけを加算するのが定石である。
    - 適用条件: 局所変更が局所影響に閉じる。
    - 期待効果: 評価関数の大幅高速化。
    - 注意点: 差分式のバグがスコア破綻に直結する。

-   13. 履歴スタックによる巻き戻し（Rollback）
    - 事実: 状態全体をコピーするより、変更箇所だけを戻す方が巻き戻しのコストは小さい。
    - 意見: 変更箇所と旧値のみを戻す方式が有効である。
    - 適用条件: 焼きなましなどで却下が多い。
    - 期待効果: コピーコスト削減。
    - 注意点: 変更ログの積み忘れが致命傷。

-   14. 世代スタンプ（Generation Stamp）
    - 事実: 配列全体の初期化は要素数に比例して重くなる。
    - 意見: 世代番号で訪問管理すると初期化コストを抑えやすい。
    - 適用条件: 訪問配列の全消去が重い。
    - 期待効果: 初期化コストをほぼ定数化。
    - 注意点: 世代番号の周回対策が必要。

-   15. ゾブリストハッシュ（Zobrist Hashing）
    - 事実: 状態全体を毎回比較するより、更新可能なハッシュ値を持つ方が軽い。
    - 意見: 重複状態判定が頻発するなら、XOR更新可能なハッシュを使う価値がある。
    - 適用条件: 重複状態判定が頻発。
    - 期待効果: 重複検出の定数倍改善。
    - 注意点: 衝突はゼロではないため、重要箇所は二次確認を検討。

-   16. ビットボード
    - 事実: 真偽配列を整数ビット列に圧縮すると、同時に複数マスを処理できる。
    - 意見: 二値状態が多い盤面では、整数ビット列に圧縮して処理するのが有効である。
    - 適用条件: 二値状態が多い盤面。
    - 期待効果: 判定処理の高速化。
    - 注意点: 盤面サイズがワード境界をまたぐと実装が複雑化。

-   17. PopCount と CTZ の活用
    - 事実: 立っているビット数や最下位ビット位置は、専用命令で高速に求められることが多い。
    - 意見: 立っているビットの列挙や個数計算は、専用命令に乗る形で取得するのがよい。
    - 適用条件: 立っているビットの列挙や個数計算が多い。
    - 期待効果: 手書きループより高速なことが多い。
    - 注意点: ゼロ入力時の挙動を仕様通りに扱う。

-   18. シフト演算による一括近傍判定
    - 事実: シフトと論理演算で、近傍条件を盤面全体に対してまとめて判定できる。
    - 意見: 近傍規則が単純な格子なら、シフト演算でまとめて判定するのがよい。
    - 適用条件: 近傍規則が単純な格子。
    - 期待効果: 命令数削減。
    - 注意点: 行端の回り込み防止マスクが必須。

-   19. 分岐削減（Branchless化）
    - 事実: 分岐予測ミスが多いと、単純な if でも性能が落ちることがある。
    - 意見: 比較結果の数値化などで分岐を減らすとよい。
    - 適用条件: 分岐予測ミスが多い箇所。
    - 期待効果: パイプライン停滞の緩和。
    - 注意点: 常に速いとは限らないため、必ず計測で確認。

-   20. 遷移先リストの事前計算
    - 事実: 境界チェックや近傍生成を毎回行うより、事前計算して参照する方が軽い。
    - 意見: 事前計算して参照するのがよい。
    - 適用条件: グラフ構造が固定。
    - 期待効果: ループ内分岐の削減。
    - 注意点: メモリ使用量とのトレードオフ。

-   21. ルックアップテーブル
    - 事実: 離散的な入力に対する高コスト計算は、表にしておくと参照だけで済む。
    - 意見: 高コスト関数や離散引数の計算はテーブル化するとよい。
    - 適用条件: 入力パターンが有限または粗い離散化で許容。
    - 期待効果: 高価な演算の置換。
    - 注意点: テーブル誤差とキャッシュ圧迫を評価する。

-   22. 数値表現の見直し（整数化を含む）
    - 事実: 浮動小数点が常に遅いとは限らず、整数化で精度や実装の安定性が上がる場合がある。
    - 意見: ホットループでの演算量と精度要件を見て選ぶべきである。
    - 適用条件: 反復回数が多く、演算コストが支配的。
    - 期待効果: 安定した実行時間や再現性向上。
    - 注意点: スケーリング誤差とオーバーフロー管理が必要。

-   23. 軽量乱数生成器
    - 事実: 乱数生成器の状態が大きいと、呼び出しコストが無視できなくなることがある。
    - 意見: 状態が小さい乱数を使うとよい。
    - 適用条件: 乱数呼び出し回数が非常に多い。
    - 期待効果: 乱数生成の定数倍改善。
    - 注意点: 品質不足は探索性能を落とすため、複数シード検証を行う。

-   24. 小関数のインライン化
    - 事実: 呼び出しオーバーヘッドは、短い関数を大量に呼ぶと目立つことがある。
    - 意見: 頻出の短い関数はインライン候補にするとよい。
    - 適用条件: 呼び出しオーバーヘッドが無視できない。
    - 期待効果: 関数境界コストの削減。
    - 注意点: 強制インラインの乱用はコード肥大で逆効果になり得る。

-   25. 境界チェック削減を促す記述
    - 事実: 配列アクセスが多いと、境界チェックの積み重なりが無視できなくなることがある。
    - 意見: コンパイラが安全に最適化しやすい形で書くとよい。
    - 適用条件: 配列アクセスが支配的。
    - 期待効果: 不要チェックの削減。
    - 注意点: 安全性を壊す最適化は最終手段に留める。

-   26. ハッシュ実装の見直し
    - 事実: 連想配列アクセスがボトルネックなら、ハッシュ実装の差が効くことがある。
    - 意見: 高速なハッシュ実装を検討する価値がある。
    - 適用条件: 連想配列アクセスがボトルネック。
    - 期待効果: 挿入検索の定数倍改善。
    - 注意点: 速度差はデータ分布依存。

-   27. 短絡評価の順序最適化
    - 事実: 短絡評価では、左側の条件が失敗すると右側を評価しない。
    - 意見: 軽い判定または失敗しやすい判定を先頭に置くとよい。
    - 適用条件: 条件式が高頻度評価される。
    - 期待効果: 不要評価の早期打ち切り。
    - 注意点: 可読性とのバランスを取る。

## 2.3 よく使われる計算量削減

ここは計算量の削減に関する実務的な定石であり、定数倍より先に効くことが多い。
まずここを疑うと、無駄な最適化を避けやすい。

-   28. 候補削減（Pruning）
    - 事実: 全部の候補を評価せず、見込みが薄いものを先に落とせば、探索木の分岐数は小さくなる。
    - 意見: まず軽いスコアで上位だけ残し、その後に重い評価をかける構成が扱いやすい。
    - 効果: 典型的には探索木の分岐数を大きく削れる。

-   29. 枝刈りの早期終了
    - 事実: 途中で上界・下界が悪くなった分岐を打ち切れば、不要な計算を減らせる。
    - 意見: DPやビーム探索では、現在最良より明らかに悪い分岐を切るのが定石である。
    - 効果: 無駄な深掘りを減らす。

-   30. 段階評価（粗→細）
    - 事実: 近似評価で候補を絞ってから厳密評価すると、重い関数の呼び出し回数は減る。
    - 意見: 距離や衝突数の粗い指標で候補を減らしてから最終判定する構成が分かりやすい。
    - 効果: 重い評価関数の呼び出し回数を減らせる。

-   31. 重複状態の除去
    - 事実: 同じ状態や支配された状態を再探索しなければ、探索空間は縮む。
    - 意見: ハッシュや canonical 化で同型状態をまとめる方法が使いやすい。
    - 効果: 探索空間そのものを縮められる。

-   32. 支配関係の利用
    - 事実: ある状態が別の状態より明らかに劣るなら、捨てることで探索対象を減らせる。
    - 意見: 同じ進行度ならスコアの悪いものを残さない、という基準は扱いやすい。
    - 効果: ビーム幅や候補集合を自然に小さくできる。

-   33. 前処理による問い合わせ削減
    - 事実: 前処理結果を参照すれば、毎回の探索や再計算を減らせる。
    - 意見: 距離表、到達可能性、連結成分、prefix sum、imos はまず疑うべきである。
    - 効果: 繰り返し計算の多い問題で大きく効く。

-   34. 部分問題への分割
    - 事実: 全体を独立または準独立な部分に分ければ、1回あたりの計算量を下げられる。
    - 意見: 連結成分ごと、行・列ごと、時間帯ごとに分ける設計は実用的である。
    - 効果: 1回あたりの計算量と実装の複雑さを同時に下げやすい。

-   35. 小さい部分だけ厳密に解く
    - 事実: 小さい部分だけ厳密に解き、大きい部分は別の手法に任せる構成は可能である。
    - 意見: 候補数が少ない場面だけ bit DP や全列挙に切り替えるのが使いやすい。
    - 効果: 「小さいところは完全解法、大きいところはヒューリスティック」に分けられる。

-   36. 動的ビーム幅の調整
    - 事実: 残り時間や候補数に応じて探索幅を変えると、時間資源を使い切りやすい。
    - 意見: 残り時間に応じて次の探索幅を動的に決めるのが実用的である。
    - 効果: 時間切れを防ぎつつ、後半の深掘りを残せる。

-   37. 二段階BFSや局所探索
    - 事実: 全域を毎回なめず、必要な区間だけ再探索すれば、再計算範囲を限定できる。
    - 意見: prefix 側と距離計算側を分けて、必要な部分だけ BFS を回す構成は有効である。
    - 効果: 再計算範囲を限定できる。

## 2.4 実戦的応用パターン

ここは実装パターンの例であり、理論ではなく応用の型を示す。
各項目は「何を組み合わせるか」が見えれば十分で、細部の実装は問題依存で調整する。

-   38. ビットボードによる高速 BFS
    - 事実: ノード集合をビット集合で持てるなら、前線をまとめて更新する形に変えられる。
    - 意見: 盤面や小さめの状態空間では、通常の queue BFS よりビットボード BFS が有効なことがある。
    - 使い方: 現在の frontier をビット集合で持ち、1手進めた隣接集合をシフトや OR でまとめて作る。
    - 向いている場面: グリッドの到達判定、障害物のない固定盤面、64個前後までの小状態遷移。
    - 注意点: 盤面が大きい場合はビット集合の分割やワード跨ぎの管理が必要になる。

-   39. フロンティア拡張の一括処理
    - 事実: 次に広がる候補を個別に push するより、まとめて計算した方が速い場合がある。
    - 意見: 隣接関係が単純なら、1層分を丸ごと更新する実装が扱いやすい。
    - 使い方: 方向ごとにシフトしたビット列を作り、壁マスクをかけて新しい frontier を作る。
    - 向いている場面: 迷路、短距離探索、到達可能マス数の計測。
    - 注意点: 層ごとの重複除去や境界マスクを忘れると誤差が出る。

-   40. ビット集合 DP
    - 事実: 状態遷移が「ある列を選ぶか選ばないか」に近いなら、bitset で遷移をまとめられる。
    - 意見: 小さい制約付き部分問題は、配列 DP より bit DP の方が実装と速度の両面で有利なことがある。
    - 使い方: 到達可能な和や状態をビット列で持ち、シフトと OR で更新する。
    - 向いている場面: 部分和、区間選択、少数候補の完全探索。
    - 注意点: 状態数が大きいとビット列のサイズが膨らみ、逆に重くなる。

-   41. 連結成分と flood fill の高速化
    - 事実: 成分探索は BFS/DFS の繰り返しで構成されるため、訪問管理の定数倍が効く。
    - 意見: 盤面が小さいなら、queue とビット集合の併用で flood fill を軽くできる。
    - 使い方: 未訪問集合を bitset で持ち、1成分ごとに取り除いていく。
    - 向いている場面: 盤面の塗り分け、連結性判定、到達領域の集計。
    - 注意点: 盤面サイズが大きいとビット集合の更新回数が増え、メリットが薄れる。

-   42. ビット演算と枝刈りの併用
    - 事実: 候補を bitset で持つと、条件を AND するだけで一括削減できる。
    - 意見: 評価が重い探索では、bitset で候補集合を先に絞ってから細かい評価をするのが有効である。
    - 使い方: 行・列・属性ごとの条件マスクを AND して、残った候補だけを見る。
    - 向いている場面: ビーム探索、制約充足、状態圧縮探索。
    - 注意点: 候補数が少ない場合は通常の配列走査の方が簡単で速いことがある。

-   43. Rollback Union-Find
    - 事実: 辺の追加で変わる親配列とサイズだけを記録すれば、結合状態は巻き戻せる。
    - 意見: 連結性を保ちながら試行錯誤するなら、経路圧縮を使わない rollback 版 Union-Find が有効である。
    - 使い方: 結合時に親とサイズの変更履歴を積み、却下時にその履歴を逆順に戻す。
    - 向いている場面: 動的連結性の確認、辺の追加削除を伴う局所探索、制約付きグラフ操作。
    - 注意点: 経路圧縮を入れると巻き戻しが難しくなるため、通常は使わない。

-   44. メモリプール化によるビームサーチ
    - 事実: ビームサーチでは状態数が多いため、個別確保の回数が性能を左右しやすい。
    - 意見: 状態を巨大な配列プールに詰め、ID 参照で扱う方式が有効である。
    - 使い方: 状態生成時はプールの次の空き領域に書き込み、親 ID と合わせて辿れるようにする。
    - 向いている場面: 毎ターン大量の子状態を作る探索、幅が大きいビーム、ノード再利用が可能な探索。
    - 注意点: プール枯渇や世代ごとの再初期化を設計しておく必要がある。

-   45. 確率のルックアップテーブルによる SA
    - 事実: 遷移受理確率の計算で exp や浮動小数点を毎回使うと、ホットパスが重くなることがある。
    - 意見: 温度と悪化量の離散化が許せるなら、受理閾値を事前計算しておくとよい。
    - 使い方: 温度段階と Δ をインデックスにして、受理するかどうかを整数比較で判定する。
    - 向いている場面: 焼きなまし、遷移評価が軽い局所探索、温度スケジュールが離散的な実装。
    - 注意点: 離散化誤差で探索性が変わるので、閾値の刻みは実験で確認する。

-   46. 2次元累積和・差分配列による矩形評価
    - 事実: 矩形内の値を毎回なめるより、累積和や差分配列を使う方がクエリコストを下げやすい。
    - 意見: 矩形の追加・削除と重なり判定が多いなら、2次元累積和や差分配列を使うとよい。
    - 使い方: 配置時は差分配列に四隅だけ更新し、評価時は必要な範囲だけ累積和を参照する。
    - 向いている場面: 矩形配置、被覆率評価、盤面上の重なり計算。
    - 注意点: 差分更新後の復元や再計算のタイミングを誤ると、評価が壊れやすい。

-   47. 独立アキュムレータによる ILP
    - 事実: 依存鎖が長い単一加算より、独立な複数加算の方が並列化しやすい。
    - 意見: ループアンローリングで集計変数を分けると、命令レベル並列性を引き出しやすい。
    - 使い方: sum0, sum1, sum2, sum3 のように複数の集計器へ振り分けて最後に合算する。
    - 向いている場面: 総和計算、距離の集計、内積、軽いスキャン処理。
    - 注意点: コンパイラ最適化で十分な場合もあるので、手書き前後で比較する。

-   48. 1次元配列によるセグ木・Fenwick 化
    - 事実: ポインタベースの木構造より、1次元配列の方がメモリアクセスは素直になりやすい。
    - 意見: 区間更新や区間和が多いなら、配列ベースのセグ木や Fenwick Tree が扱いやすい。
    - 使い方: 木を固定長配列で持ち、添字計算で親子を辿る。
    - 向いている場面: 区間加算、区間和、スケジューリング、差分管理。
    - 注意点: 問題が小さいなら素朴な配列更新の方が速くて簡単な場合もある。

## 2.5 運用ルール（最重要）

ここは実装の正解ではなく、採用判断のための意見をまとめる。
見出しどおり、最終的にはスコアと安定性で決める。

-   49. 変更は一度に1つ
    - 意見: 複数変更を同時投入すると、効果と退行の原因が追えないため、一度に1つずつ変えるべきである。

-   50. 固定シードで before after を比較
    - 意見: 反復回数、最終スコア、実行時間は同条件で記録すべきである。

-   51. 速さだけで採用しない
    - 意見: 速度向上で探索の質が下がる場合は不採用にすべきであり、最終評価はスコア基準で行う。

-   52. 期限直前は安全策
    - 意見: 提出直前は大改造を避け、検証済み最適化のみ残すべきである。
